# 柴犬探偵団 〜リビングに消ゆ〜 設計書

- 作成日: 2026-07-10
- 原典: Google Docs `1tDFiPNUDGyXECjdaxOaH3Mq74cjrnWJ_m2dt_C8OucY`
- ステータス: 設計確定・実装前

## 1. 概要

2人の人間（じゅんこ・たいち）と3頭の柴犬（雷蔵・はな・蔵之介）による、ザッピング式コマンド選択テキストアドベンチャー。ビジュアルは80〜90年代のPC-8800シリーズ風（黒背景・蛍光モノクローム）。1周15〜20分。

原典仕様書から意図的に変更・追加した点は §8 にまとめる。

## 2. 技術構成

| 項目 | 選択 | 理由 |
|---|---|---|
| フロント | Vanilla JS（ESモジュール） | 既存プロジェクト（ShibaCare / GACHI-FIT / Voice Journal）と統一。ビルド不要でGitHub Pagesに直接公開できる |
| スタイル | 素のCSS | PC-8800風UIは装飾が少なく、フレームワークの利得がない |
| 同期 | Firebase Realtime Database + 匿名認証 | 2人同時プレイのため。ゲーム専用の新規Firebaseプロジェクトを作成し、ShibaCareの健康データとは分離する |
| テスト | `node --test test/*.test.js` | 既存プロジェクトと同じ |
| 配信 | GitHub Pages + PWA | オフラインで1人プレイが成立する |

原典は Next.js + Tailwind を指定していたが、本作に動的サーバー機能は不要であり、既存資産との一貫性を優先した。

## 3. アーキテクチャ方針：ローカルファースト＋ミラー

ゲーム状態の正はブラウザ内メモリに置く。コマンド選択のたびに純粋関数でフラグを更新し、その差分を RTDB に書き戻す。相手の変更は購読して取り込む。

この構えを選ぶ理由は3つ。エンジン（条件評価・フラグ適用・エンディング判定）が完全な純粋関数になりネットワーク抜きにテストできること。コマンド選択に往復待ちが入らずレトロADVのテンポが保てること。通信が切れてもプレイが止まらないこと。

本作のフラグは増える一方（単調増加）で競合がほぼ起きないため、最終書き込み優先の素朴なミラーで破綻しない。例外はバディ選択のみで、そこだけトランザクションで守る（§5.2）。

## 4. シナリオデータとエンジン

### 4.1 データ形式

シナリオは静的JSON 1枚（`data/scenario.json`）。シーンIDをキーにした辞書。

```json
{
  "sceneId": "ch2_taichi_shimabaraya",
  "route": "taichi",
  "chapter": 2,
  "locationName": "藤原2組 しまばらや前",
  "art": "shimabaraya",
  "description": "昼だけ営業している地元のスーパー。だいき君が配達の準備をしている。",
  "dialogue": [
    { "speaker": "たいち", "text": "ふぅ、佐世保駅の方まで探したけど手掛かりゼロだ。" },
    { "speaker": "だいき", "text": "おや、たいちさん。お散歩ですか？" }
  ],
  "commands": [
    {
      "text": "▶きく（事件について）",
      "next": "ch2_taichi_shimabaraya_listen",
      "setFlag": "info_satoru_bag"
    },
    {
      "text": "▶みつめる（美女を）",
      "next": "ch2_taichi_shimabaraya_look_girl",
      "count": "taichi_mitsumeru",
      "condition": { "buddyNot": "hana" }
    }
  ]
}
```

`route` は `"junko" | "taichi" | "common"`。`art` は §6.2 のドット絵ID。

### 4.2 条件式

原典のサンプルは `"condition": "if_not_hana"` という文字列だったが、オブジェクトに変更する。文字列だと条件が増えるたびに `if_` で始まる名前をエンジン側にハードコードすることになり、シナリオを書くたびにコードを触ることになる。オブジェクトなら評価器は一度書けば終わる。

```
{ "flag": "found_black_hair" }        フラグが立っている
{ "buddy": "raizo" }                  自分のバディが雷蔵
{ "buddyNot": "hana" }                自分のバディがはな以外
{ "support": "kuranosuke" }           お留守番が蔵之介
{ "countAtLeast": ["taichi_mitsumeru", 3] }
{ "allOf": [ ... ] }  { "anyOf": [ ... ] }  { "not": { ... } }
```

### 4.3 エンジン API（`src/engine.js`）

ネットワークもDOMも知らない純粋関数のみ。

- `evaluate(condition, state) -> boolean`
- `visibleCommands(scene, state) -> Command[]`
- `applyCommand(state, command) -> newState`（フラグ立て・カウンタ加算・シーン遷移）
- `resolveEnding(state) -> "A" | "B" | "C" | "D"`

### 4.4 フラグとカウンタ

| フラグ | 取得元 | 章 |
|---|---|---|
| `evidence_mud` | じゅんこ：ソファを調べる | 1 |
| `evidence_black_hair` | じゅんこ：ソファを調べる | 1 |
| `heard_shadow` | たいち：両親に聞き込み | 1 |
| `suspicious_father` | たいち：両親に聞き込み | 1 |
| `info_black_cat` | じゅんこ：井上肉店のおばちゃん | 2 |
| `info_satoru_bag` | たいち：だいき君 | 2 |
| `found_empty_box` | 蔵之介の狂犬化 / 雷蔵の嗅覚 | 3 |
| `taichi_delay` | 派生（下記） | 2〜 |

`taichi_delay` は真偽値ではなく累積で決まる。カウンタ `counters.taichi_mitsumeru` が **3以上**になった時点で立つ。原典の「『みつめる』を多用すると立つ」を機械的に定義したもの。

フラグは二人の**共有プール**。じゅんこが取ったフラグはたいちのものでもある。エンディング条件が route をまたぐ（Aは たいち＋犬、Bは じゅんこ＋じゅんこ）ため、これは原典が要求している形。

### 4.5 エンディング判定

原典はA・B・Cの条件のみを定義し、(1) AとBが両方揃った場合 (2) A・Bとも不成立で `taichi_delay` も立たない場合、を定義していない。以下で確定する。

```
A条件 = suspicious_father && found_empty_box
B条件 = evidence_black_hair && info_black_cat

A条件 && B条件  -> D
A条件           -> A
B条件           -> B
それ以外        -> C
```

- **A（お父さん主犯）**: 孫バカなお父さんの犯行。
- **B（黒猫の義賊）**: 黒兵衛が地域犬たちとシェアしていた。
- **C（たいち完全自爆）**: たいちが酔って隠しただけの自作自演。証拠不足の受け皿を兼ねる。`taichi_delay` が立っている場合のみ、寄り道を責められる追加の一幕が入る。
- **D（新規・真エンド）**: 柴犬たちは最初から全部知っていた。雷蔵は匂いで黒兵衛を、はなは父の嘘を、蔵之介は空箱の在り処を——三頭とも真相を知りながら、それぞれの理由で黙っていた。人間ふたりが証拠を出し揃えて初めて、リビングで三頭が遠吠えする。第4章の題「リビングに響く遠吠え」の回収。

AとBは「お父さんが犯人」「黒兵衛が犯人」で両立しない。両方の証拠が揃うのは全部を探ったプレイヤーだけなので、そこに四つ目の結末を置く。

### 4.6 犬の固有コマンド

| 犬 | コマンド | 効果 |
|---|---|---|
| 雷蔵 | ▶クンクンする | 見えない匂いのフラグを発見。第3章では箱の隠し場所を当てる |
| はな | ▶ジロリとみる | 間違った推理やNPCの嘘を正す。`buddyNot: "hana"` により、はな同伴時は「みつめる」等の無駄コマンドが出ない |
| 蔵之介 | ▶へそ天 | 基本は無駄行動。特定フラグ下で「狂犬化」し証拠を噛みちぎる（`found_empty_box`） |

蔵之介の狂犬化は原典で「高確率」とされるが、**乱数を使わず確定条件にする**。ザッピングで得た証拠が結末を決めるゲームで、結末に直結する `found_empty_box` を運に委ねると、プレイヤーの推理が報われない周回が生まれる。条件は「第3章に `info_satoru_bag` を持って到達し、蔵之介がバディである」。

### 4.7 お留守番（サポート犬）

選ばれなかった1頭が両ルートに割り込んでヒントを出す。`scenario.json` の各シーンに任意で `supportHint` を持たせ、`{ "support": "kuranosuke" }` 条件で出し分ける。これも乱数を使わず、シーン固定で置く。

## 5. 2人プレイの同期

### 5.1 RTDB データ形

```
rooms/{4桁コード}/
  createdAt, expiresAt          24時間で失効
  phase: "lobby"|"playing"|"finale"|"ended"
  supportDog: "kuranosuke"
  ending: "D"
  players/junko/  { uid, buddy, sceneId, chapter, chapterDone }
  players/taichi/ { uid, buddy, sceneId, chapter, chapterDone }
  flags/    { evidence_black_hair: true, ... }
  counters/ { taichi_mitsumeru: 2 }
  feed/     { pushId: { ts, route, text } }
```

片方が4桁コードで部屋を作り、もう一方が参加。匿名認証（`signInAnonymously`）でログイン不要。セキュリティルールは「認証済みユーザーは任意のルームを読み書きできる」＋「`expiresAt` 超過を弾く」の最小構成。身内で遊ぶゲームであり、不正対策は要件に含まない。

### 5.2 唯一の競合：バディ選択

二人が同時に雷蔵を押すと両方が雷蔵になり、お留守番が決まらない。`players/{route}/buddy` への書き込みをトランザクションで行い、既に相手が確保した犬は選択不可に落とす。

### 5.3 feed（実況）

相手がフラグを取ると、自分の画面下部に一行流れる。

> たいち：しまばらや前で、さとる君の紙袋の話を聞いた

相手の画面を覗くのではなく、**相手が何を掴んだかだけ**が伝わる。第4章で突き合わせるまで、全体像はどちらにも見えない。文面はフラグごとに `scenario.json` の `feedText` で定義する。

### 5.4 第3章：電話越しの共犯

原典は第3章を「共通」とするが、さとる君と対峙するのはたいちひとりで、じゅんこは家にいる。2人プレイでは以下のように解釈する。

じゅんこ側に第3章で `▶推理を送る` コマンドが解禁される。それまでに取ったフラグに応じた推理を送れる。たいち側の画面には、送られてきた推理が**コマンド選択肢として増える**。じゅんこが `info_black_cat` を持っていれば、たいちは「黒猫を見なかったか」と訊けるようになる。持っていなければその選択肢は存在しない。

原典にない発明だが、「片方だけでは真相に届かない」というザッピングの主題を最も強く出せる場所がここである。

### 5.5 第4章のゲートと離脱耐性

`players/*/chapterDone` が両方立ったら `phase: "finale"` に遷移し、以降は同じシーンを同期して見る。

片方が離脱している場合、残った側に「ひとりで結論を出す」ボタンを出し、現在のフラグで判定を走らせる（多くはC）。原典の「ゲームオーバーが存在しない」を守るため、詰み状態を作らない。

## 6. UI

### 6.1 レイアウト

原典の3ペインをそのまま採る。

```
+-------------------------------------------------------------+
| [場所: 藤原2組 しまばらや前] [バディ: 雷蔵] [視点: たいち]  |
+-------------------------------------------------------------+
|                  （SVGドット絵ペイン）                       |
+-------------------------------------------------------------+
| たいち「だいき君、このへんで怪しい奴を見なかったか？」       |
| 雷蔵「クンクン…！その話、匂うぜ、たいち！」                  |
+-------------------------------------------------------------+
| 【コマンド】                                                 |
| [1. しらべる] [2. きく] [3. バディに頼む] [4. いどう] ...    |
+-------------------------------------------------------------+
```

数字キー1〜5で選択、Enterで送り、Spaceで早送り。キーボードのみで完結させる（PC-88にマウスはない）。スマホでは同じ配置を縦に積み、タップで選択。

### 6.2 レトロ表現

- 黒背景に蛍光モノクローム。**緑／アンバー／白**を設定で切替（原典指定）
- 等幅フォント、1文字ずつのタイプライタ表示
- 薄いスキャンライン
- WebAudio の矩形波で文字送り音とフラグ取得ジングル。**初期はオフ**

SVGドット絵は場所7枚（リビング、坂道、しまばらや前、井上肉店、佐世保駅、基地の街、玄関）と犬3頭の顔。`src/ui/art.js` にIDで引ける関数として置き、シーンの `art` から参照する。後でPNGに差し替える場合、この関数の中身を `<img>` に変えるだけで済む。

## 7. ファイル構成とテスト

```
shiba-detective/
  index.html  style.css  manifest.json  sw.js
  database.rules.json
  data/scenario.json
  src/
    main.js                 画面遷移とイベント配線
    engine.js               純粋関数（条件評価・フラグ・エンディング判定）
    state.js                ゲーム状態と localStorage 退避
    ui/ screen.js  typewriter.js  art.js  sound.js
    net/ firebase.js  room.js
  test/ engine.test.js  scenario.test.js
```

`node --test test/*.test.js`。エンジンが純粋関数なのでネットワーク抜きに全分岐を検証できる。

`scenario.test.js` は全シーンを走査して以下を機械的に確かめる。50シーンを手書きすると必ずタイポでリンクが切れるため、これが最も効く防御になる。

1. すべての `next` の参照先が実在する
2. 到達不能なシーンがない
3. 4つのエンディング条件が、実際に到達可能なフラグの組み合わせで満たせる

### エラー処理

- ネットワーク断：ローカルでプレイ続行、復帰時に差分を書き戻す
- ルームコードが不在・失効：ロビーに戻して明示
- Firebase 初期化失敗：**1人プレイに自動フォールバック**（両視点を手動切替）。ゲームが起動しないより望ましい

PWA（manifest + Service Worker）でシナリオJSONごとキャッシュし、オフラインで1人プレイが成立する。

## 8. 原典仕様書からの変更点

| # | 変更 | 理由 |
|---|---|---|
| 1 | Next.js + Tailwind → Vanilla JS + 素のCSS | 動的サーバー機能が不要。既存プロジェクトと統一 |
| 2 | 1人プレイ想定 → 2人同時プレイ（ルームコード＋RTDB） | ユーザー選択 |
| 3 | `condition` を文字列からオブジェクトへ | 条件追加のたびにエンジンを触らずに済む |
| 4 | `taichi_delay` をカウンタ由来（みつめる3回以上）に定義 | 原典の「多用すると」を機械的に確定 |
| 5 | エンディングDを追加 | 原典はA・B両立時と全条件不成立時を未定義 |
| 6 | 蔵之介の狂犬化を「高確率」から確定条件へ | 結末に直結するフラグを運に委ねない |
| 7 | サポート犬の割り込みを乱数からシーン固定へ | 同上。ヒントの再現性を担保 |
| 8 | 第3章にじゅんこの「推理を送る」を追加 | じゅんこを1章分の傍観者にしないため |
| 9 | 音は初期オフ | 深夜プレイへの配慮 |
